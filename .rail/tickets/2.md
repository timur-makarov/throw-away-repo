## Request
> Customers and products can only be listed. For both we need create, read one, update and delete handlers, with validation of every field (names not empty, a product's price a non-negative number of cents, a customer's email shaped like an email), paging on both lists, a CSV export for each like the orders one, and tests for all of it. `docs/api.md` should describe every new handler.

## Why
Customers and products can only be listed today, so nothing can be added or corrected through the handlers. The whole request (CRUD, validation, paging and CSV for two record kinds, plus tests and docs) is well over the 600-line cap in one ticket, so this ticket is the first slice: create, read one and update for customers, with validation. It is the smallest part that can be checked alone and that the other slices copy.

## Done Contract
- Check: `python3 -m pytest -q tests/test_customers.py -k create_customer`
- Check: `python3 -m pytest -q tests/test_customers.py -k get_customer`
- Check: `python3 -m pytest -q tests/test_customers.py -k update_customer`
- Check: `grep -q 'api.create_customer' docs/api.md && grep -q 'api.get_customer' docs/api.md && grep -q 'api.update_customer' docs/api.md`

## Out of scope
- Delete, paging and CSV export for customers (slice 2).
- Anything for products (slices 3 and 4).
- Changes to `shop/store.py`, `shop/auth.py` or `migrations/`: this slice uses `store.save_customer` and `store.list_customers` only.
- The existing `api.list_customers` answer does not change.

## Assumptions
- VERIFIED: a customer has the fields `id`, `name` and `email`; `name` must be a non-empty string after trimming, and `email` must have the shape `local@domain.tld` (one `@`, no spaces, a dot in the domain). Checked: checked `shop/store.py`, `migrations/` and AGENTS.md: no customer shape or validation rule exists, so the request's "names not empty" and "shaped like an email" is the only source; a design choice the request leaves open.
- VERIFIED: `create_customer` takes the next id itself (the highest stored id plus 1, or 1 when none), because the request names no id source. Checked: checked `shop/store.py`: `save_customer` keys by `customer["id"]` and has no id counter, and the request names no id source; the sorted-by-id `list_customers` makes max+1 derivable through the store, as AGENTS.md requires.
- VERIFIED: a successful create answers `{"status": 200, "customer": {...}}`, following the AGENTS.md convention of 200 for success, not 201. Checked: AGENTS.md Conventions: a handler returns `{"status": 200, ...}` on success; `get_order` in `shop/api.py` does the same.
- VERIFIED: bad input answers `{"status": 400, "error": "..."}`; a missing customer answers 404, as `get_order` does. Checked: AGENTS.md: `{"status": 4xx, "error": "..."}` and handlers do not raise; `get_order` returns 404 with `error` for a missing record (`tests/test_orders.py` asserts it).
- VERIFIED: update replaces `name` and `email` together (both are validated), and does not change the id. Checked: design choice the request leaves open; `save_customer` replaces the whole record by id, so saving with the found id keeps the id.
- VERIFIED: with no `get_customer` in `shop/store.py`, read one scans `store.list_customers()`. Adding a store function would make the ticket PERSON, so it is left for a later slice. Checked: read `shop/store.py`: it has `list_customers` and `save_customer` only; the ticket's Out of scope and scope_paths exclude `shop/store.py`, and the task brief says a store change makes it PERSON.

## Look at
- Check first: `_customer_fields` email pattern (`shop/api.py`): `local@domain.tld`, no spaces, one `@`, non-empty dot-separated domain labels (so `a@.com`, `a@x.` and `a@x..com` are rejected). The name is stored trimmed; the email is stored as given.
- `_find_customer` scans `store.list_customers()` (marked `SHORTCUT(2)`); update validates after the 404 check, so a missing id with bad fields answers 404.
- Reuse: no helper for validation or a get-one existed; stdlib `re` is used. No store, auth or migration change: the stored shape is unchanged.
- Not tested: concurrent creates (the in-memory store has no locking, so max+1 can collide), and non-int ids in requests beyond a missing id, because the store only holds what callers save.
- Noticed, left alone: `api` handlers do not call `auth.allowed`; the ticket did not ask for it.
