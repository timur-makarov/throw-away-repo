## Request
> We sell some things by weight. `quantity` may be a decimal such as 0.25, and each line's amount rounds down to the whole cent before the lines are added up. Today `total` returns a float for such an order.

## Why
Orders sold by weight need a quantity such as 0.25. Today `orders.total` multiplies cents by quantity, so a fractional quantity gives a float total, which breaks the rule that money is an integer number of cents. Each line must round down to the whole cent first, then the lines are summed. `export.orders_csv` and `orders.summary` both call `orders.total`, so both follow. The stored shape also changes: `order_lines.quantity` is INTEGER in `migrations/0001_orders.sql`, so a numbered migration comes with it (AGENTS.md), which makes this ticket PERSON.

## Done Contract
- Check: `python3 -m pytest -q tests/test_orders.py -k fractional_quantity`
- Check: `python3 -m pytest -q tests/test_orders.py -k each_line_rounds_down`
- Check: `grep -Eqi 'quantity[^,;]*(NUMERIC|DECIMAL)' migrations/0002_quantity_numeric.sql`

## Out of scope
- `shop/export.py` and `shop/api.py`: they call `orders.total` and need no change; the existing export test must keep passing.
- The discount code (ticket 7) and the order status (ticket 5).
- Integer quantities keep their present totals.

## Assumptions
- ASSUMED: amounts are computed with exact decimal arithmetic (for example `Decimal(str(quantity))`), not binary floats, so 0.1 times 30 cents is 3 and not 2.9999.
- ASSUMED: quantities and cents are not negative, so rounding down and truncating agree.
- ASSUMED: `total` returns an `int` for every order, including ones with integer quantities.
- ASSUMED: the migration is named `0002_quantity_numeric.sql` (the next number after 0001) and keeps its down step in the same file as a commented `-- down` section, since the repository has no other down-file convention.
- ASSUMED: the stored column type for the decimal quantity is NUMERIC; the in-memory store needs no change.
